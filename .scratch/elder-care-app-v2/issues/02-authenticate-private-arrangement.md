## Acceptance criteria

- [ ] Use approved email codes and protected retained sessions; preserve identity-owned arrangement and prepared need across returning use and original-email replacement-device sign-in.
- [ ] Preserve secure sessions across ordinary closure/reopening without daily email-code sign-in. Preserve the intended 30-day inactivity timeout measured by successful session refreshes, not a custom human-activity estimate; its hosted configuration/verification is the deferred environment gate below, not a Cloud Free implementation requirement. Restrict routine automatic refresh to appropriate active/foreground behavior; no continuous background refresh process or unnecessary fixed maximum session lifetime.
- [ ] Require email-code reauthentication when the session has actually expired; preserve explicit sign-out, appropriate lost-device session revocation and current backend permission/session-validity checks. JWT expiry or refresh alone must not be treated as immediate revocation. Offline information and pending reports retain their separately approved lifecycle boundaries.
- [ ] Use local Supabase development and/or Cloud Free with synthetic care information as appropriate within the approved US$0/month Supabase development budget. Test supported local elapsed-inactivity behavior separately from current-session revocation, foreground/resume and connectivity failures. Never label Cloud Free as enforcing the Pro-only hosted timeout, substitute a custom inactivity framework or activate paid services. No routine biometrics or repeated authentication for normal coordination.
- [ ] Store complete authenticated sessions in isolated SQLCipher-protected local storage with SecureStore-protected keys, secure restoration and no plaintext fallback; do not assume the session fits a single SecureStore value. Preserve anonymous/account separation.
- [ ] Configure email sign-in codes with ten-minute validity and a minimum sixty-second resend interval, supported server-side request/verification rate limits and clear expired-code/retry handling. Never log codes, refresh tokens or other authentication secrets. Test incorrect, expired and reused codes and direct-endpoint throttling.
- [ ] Start with one-hour access tokens while preserving the approved refresh-based inactivity policy and foreground refresh. Ordinary sign-out must explicitly target the current session using Supabase's local sign-out scope, not its default global scope. A clearly explained, appropriately email-code-reauthenticated lost-device action may revoke other sessions without routine extra authentication for ordinary coordination.
- [ ] Verify permitted and denied protected reads and consequential operations against current arrangement permissions and relevant backend session validity, including previously issued tokens after session revocation. Refresh-token termination alone is insufficient. Distinguish local credential removal from acknowledged server revocation when disconnected; do not claim immediate recall of offline copies.
- [ ] Test direct anonymous/other-identity access and forged ownership denial. Provide normal navigation and safe sign-out without shared credentials or implied collaboration authority.
- [ ] After email-code authentication, offer a deliberate, understandable association of the private draft with the identified account, ideally one clear action without reentering its contents. Authentication alone must not upload/disclose the draft, invite participants or establish sharing authority.
- [ ] Persist an associated arrangement privately for its authenticated owner. A retried or interrupted association must neither duplicate the need nor lose the protected draft; remove redundant anonymous content only after acknowledged success. Never automatically attach it to another account following a session change.
- [ ] Apply the approved anonymous-draft lifecycle: no automatic fixed-inactivity draft expiration; obvious deliberate discard; on explicit sign-out/account switching, warn and allow canceling the transition or discarding an unassociated draft and continuing. Never silently transfer content across accounts. Retention/deletion review before real-information use still applies.
- [ ] Verify ordinary restart/session restoration, association interruption and retry, explicit draft deletion, sign-out and account-change isolation on iOS and Android. A never-associated draft has no required cross-device recovery; an associated private arrangement retains legitimate stable-identity access on a replacement device.
- [ ] Apply ticket 01's approved Expo SQLite/SQLCipher and SecureStore-key architecture to protected local draft/account information, preserving anonymous/account separation, supported Expo configuration and Continuous Native Generation. Verify native encryption before protected writes and actual iOS/Android persistence, backup/key failure, interrupted-write and reinstall behavior. No plaintext fallback, sensitive logs or mandatory routine biometric prompts; Expo Go/web testing does not establish equivalent protection.
- [ ] Deliver a demonstrable complete path through ordinary accessible user interaction, necessary backend enforcement and persistence, and focused observable tests; evaluation slices exercise delivered paths instead of implementing missing capabilities.
- [ ] Keep steps minimal: no unnecessary repeated entry, required comments, approval rounds or confirmations. Support readable scalable text, accessible controls/targets, nonsound status information, predictable navigation and recoverable input errors on iOS and Android.
- [ ] Test permitted and denied actions at the actual backend boundary, including direct requests, other arrangements, current revoked/restricted permissions and attempted privilege escalation where relevant. Never depend on interface hiding, stale token permissions or loading restricted fields into an otherwise accessible record.
- [ ] Preserve applicable information audiences across this slice's interface, backend, local data, logs, notifications and external outputs. Optional health information is protected by authorized context, never by automatic sensitive-text detection.
- [ ] Keep automated correctness/security tests distinct from observed human usability evidence. Prefer focused boundary/integration checks and minimal useful test seams over excessive mocks or infrastructure.
